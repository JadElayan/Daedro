How it works

Paired comparisons, so every difference is your change.

Both versions face identical conditions: same parts, same friction, same noise seed. If an outcome flips, the controller change caused it, not luck in which tests were drawn. That's what makes a few hundred simulated runs worth acting on.

01

Declare the envelope

Write down the conditions your cell is meant to handle. Only failures inside them count.

[suite.envelope]
mass     = [0.05, 1.0]
friction = [0.2, 1.2]
02

Open a pull request

CI runs the base and the PR version on the same seeded scenarios and comments the report.

daedro ci \
  --base-ref origin/main \
  --fail-on 0
03

Replay any failure

Every regression comes with an exact command that reproduces it, bit for bit.

daedro repro \
  --config daedro.toml \
  --scenario 137

Honest scope

What works today, and what doesn't yet.

We'd rather you trust a small claim than doubt a big one.

Works now

  • MuJoCo simulation of a Franka Panda (MuJoCo Menagerie model) doing pick-and-place
  • Comparing two parameterised controller versions on identical seeded scenarios
  • Paired statistics (exact McNemar test), regression clustering, one-line replay
  • CLI and a GitHub Action that comments on pull requests
  • Physics sanity check: grasp outcomes agree with the Coulomb friction bound in 80 of 81 grid cases

Not yet

  • Running your own learned policy or your own robot model
  • Other simulators (Isaac, ManiSkill) or tasks beyond pick-and-place
  • Any hardware validation. A pass in simulation does not guarantee real-world performance or safety.

The name

Why Daedro

“Fly the middle course.”

Daedalus, the craftsman of Greek myth, built statues that moved and wings that flew. He told Icarus to stay within the limits they'd been made for: not too high, not too low. Icarus didn't. Daedro is for teams who want to know their machine's limits before it leaves the ground.
